Hardening Item #3 — Dual-Backend State Sync
Critical
Shared Redis store for online status: Node.js (Socket.IO) owns real-time connection events and writes online status to Redis. Spring Boot's /users/online endpoint reads from the same Redis key — no direct DB polling. This eliminates the state desync risk between the two backends.
Phase 3 P2P Connection Layer — Brokering, TCP, NAT & TLS Core P2P ▼
Connection Brokering
Spring Boot /connect endpoint — accepts peer A request, notifies peer B via Node.js, returns B's IP/Port to A. Then steps out.
TCP Socket Layer
Java P2PConnection class — manages ServerSocket + Socket lifecycle on both ends. Desktop-app deployment model (local Java app per user).
NAT Traversal (STUN)
STUN-based hole punching for peers behind routers/firewalls. Discover public IP + port mapping.
TURN Relay Fallback
TURN relay server — if STUN fails (symmetric NAT), peers fall back to server-relayed TCP through TURN.
TLS Cert Pinning
Server brokers exchange public key / self-signed cert fingerprints during negotiation. Peers pin fingerprints before TLS handshake.
Spring Boot: /connect endpoint — peer A requests connection to B, server notifies B via Node.js signalling, returns B's address + cert fingerprint to A
Node.js: WebSocket signalling events — connection_request, connection_accept, connection_reject between peers
Java: P2PConnection class — opens ServerSocket on random port, connects to peer's socket, manages read/write streams
STUN: Integrate STUN client in Java — discover public IP/port, exchange via broker
TURN: Deploy TURN relay server (e.g., coturn). Java client attempts direct → STUN → TURN relay in that order
TLS: Generate self-signed certs per user. Broker exchanges fingerprints. SSLContext with pinned fingerprint verification in Java
Hardening Items #1, #2, #4 — NAT Fallback, Deployment Model, TLS Pinning
Critical
#1 TURN relay fallback: STUN is designed for UDP NAT traversal; TCP hole punching is significantly harder and unreliable across symmetric NATs. Implement a TURN relay server as fallback from day 1 — if STUN-based TCP punching fails, peers fall back to server-relayed TCP through TURN.
Critical
#2 Deployment model — confirmed: Browsers cannot open raw TCP sockets. The architecture requires each user to run a local Java application (Spring Boot) that serves the React UI locally and manages the P2P TCP socket layer. This is a desktop-style deployment model, not a pure browser app. If a pure browser app is needed, swap raw TCP for WebRTC DataChannels.
New
#4 TLS certificate pinning for P2P: Raw TLS between peers requires trust establishment. During connection negotiation (brokering phase), the server exchanges each peer's public key / self-signed cert fingerprint. Peers pin these fingerprints — TLS connection is only established if the remote cert matches the pinned fingerprint. Prevents MITM on the P2P channel.
Phase 4 1-to-1 Chat UI & Message Protocol Chat ▼
Message Protocol
Define message format over TCP: JSON header (type, sender, timestamp) + body. Types: TEXT, SYSTEM, FILE_REQUEST, FILE_RESPONSE.
Chat Logic
Java reads from socket input stream, parses messages, emits events to React via WebSocket/REST callback. React sends messages to Java, which writes to socket output stream.
Chat UI
React chat window — message bubbles (sent/received), timestamps, connection status indicator, typing indicator (optional).
Reconnect Logic
Heartbeat ping/pong every 15s. On timeout, attempt reconnect. Show "Reconnecting…" state in UI.
Protocol: MSG_TYPE|SENDER_ID|TIMESTAMP|BODY over TCP. Define TEXT, SYSTEM, FILE_REQUEST, FILE_RESPONSE, HEARTBEAT message types
Java: MessageReader thread — reads from socket InputStream, parses, forwards to React via Node.js callback or direct WebSocket
Java: MessageWriter — takes message from React (received via Node.js signalling), writes to socket OutputStream
React: Chat window component — message list, input box, send button, connection status badge, scroll-to-bottom on new message
Heartbeat: Java sends ping every 15s, expects pong within 5s. On 3 missed pongs → mark disconnected, show reconnect button
Phase 5 1-to-1 File Transfer, Chunking, Resume & Checksum File Engine ▼
File Chunking
Split file into 512KB chunks, each with sequence number. Sender reads file → chunks → sends over TCP.
Progress Tracking
Receiver logs received chunk IDs to a .part metadata file on disk. Survives full app restart.
Resume Protocol
On reconnect, receiver sends last chunk ID from .part file — sender resumes from next chunk.
Checksum
SHA-256 hash of full file verified after last chunk. Bit-perfect guarantee.
File Validation
Expanded blacklist check on sender side before transfer. MIME + extension + double-extension detection.
Protocol: FILE_REQUEST → ACCEPT/REJECT → CHUNK(n) → ACK(n) → FILE_COMPLETE → CHECKSUM_VERIFY
Sender Java: Read file as FileInputStream, split into 512KB byte arrays with sequence numbers, send over socket
Receiver Java: Read chunks from socket, write to temp file, update .part metadata file with chunk bitmap, send ACK(n)
Resume: On reconnect, receiver reads .part file → sends RESUME_FROM(chunk_id) → sender seeks to offset, resumes
Checksum: Sender computes SHA-256 of full file, sends with FILE_COMPLETE. Receiver computes SHA-256 of received file, compares.
Blacklist: Block .exe .bat .sh .msi .vbs .cmd .scr .ps1 .com by MIME + extension + double-extension check on sender side
React UI: File picker button, send file button, progress bar (chunk count / total), accept/reject dialog on receiver side, transfer complete notification
All file types: PDF, DOCX, images, video, audio, ZIP — raw binary, zero quality loss
Hardening Items #5, #6 — File Blacklist, Resume Persistence
Enhanced
#5 Expanded file blacklist: Original list (.exe, .bat, .sh, .msi, .vbs, .cmd) can be bypassed via .scr, .com, .ps1, or double extensions (e.g., file.pdf.exe). Updated blacklist: .exe .bat .sh .msi .vbs .cmd .scr .ps1 .com. Also detect double extensions by scanning the full filename, not just the last segment. Consider an allowlist mode for higher-security deployments.
Critical
#6 .part metadata file for resume persistence: Receiver writes a <filename>.part metadata file to disk containing: original filename, total chunks, received chunk bitmap, SHA-256 of partial data. On full app restart + reconnect, receiver reads this file and requests only missing chunks. If .part file is missing, transfer starts from scratch. On successful checksum verify, .part file is deleted.

Phase 7 Group File Distribution (Server-Assisted) Distribution ▼
Chunk Streaming
Sender → server → all members. Server streams chunks in memory, never stores to disk. Forward & discard.
Per-Member Tracking
Each member's chunk progress tracked independently on server. Dropouts can resume on rejoin.
Partial Delivery
If one member drops, others continue receiving. Rejoined member resumes from last acknowledged chunk.
Group Checksum
Each member verifies SHA-256 independently after receiving all chunks. Server reports per-member success.
Flow: Sender sends chunk to server → server fans out to B, C, D simultaneously → collects ACKs per member → sends next chunk
Server memory: Hold one chunk (512KB) at a time in memory buffer — forward to all members, collect ACKs, then discard. Never buffer full file.
Resume: Server tracks last_acked_chunk per member. On rejoin, server resumes from last_acked + 1 for that member only.
Checksum: Sender computes SHA-256, sends with final chunk. Each member verifies independently. Server reports per-member pass/fail to sender.
React UI: Group file send button, per-member progress bars, member status icons (receiving/done/dropped/resuming), overall completion indicator

Known limitations & mitigations
NAT/Firewall: Both users must have connectable IPs. Mitigation — STUN server for hole punching; TURN relay fallback if STUN fails (especially symmetric NAT).
Deployment model: Each user runs a local Java (Spring Boot) app that serves React UI and manages TCP sockets. Browsers alone cannot open raw TCP. Alternative: WebRTC DataChannels for pure-browser deployment.
TLS trust on P2P: Self-signed certs need trust establishment. Mitigation — server brokers exchange cert fingerprints during negotiation; peers pin them before TLS handshake.
Both online required: No offline messaging. Mitigation — optional message queue in DB for when user comes online.
Group server load: Server holds chunks in memory during group distribution. Mitigation — stream and discard each chunk immediately, never buffer full file.
Mobile P2P: TCP socket connections are harder to maintain on mobile networks. Mitigation — connection heartbeat + auto-reconnect logic.
Resume state loss: Local chunk progress lost on app restart. Mitigation — persist to .part metadata file on disk; survives restart; deleted on successful checksum.
